# Paladin should follow Apple's HIG, not OpenAI's

Apple's Human Interface Guidelines (HIG) are the only usable rulebook for a native-feeling Paladin on macOS; OpenAI's UI guidelines describe widgets embedded inside ChatGPT and transfer only for color, type, icon and contrast hygiene. Apple supplies concrete, checkable rules for the toolbar, sidebar, inspector, settings window, menus and alerts, but publishes no numeric minimum window size, no traffic-light geometry, no sidebar row heights and no command-palette or graph-canvas guidance, so those are inferences. For AI providers, the strongest design is a FastAPI backend that holds both keys in memory, talks to Claude and OpenAI through the official async SDKs behind one internal provider interface, discovers models at runtime, and streams normalized events to the renderer over loopback SSE. The renderer never sees a key; Electron's `safeStorage` encrypts it at rest in the main process; the key reaches the backend over stdin or a pipe, not argv or env. Both providers differ in ways that break a naive abstraction: Claude's flagship 5.x models reject forced `tool_choice`, `temperature` and prefill, while OpenAI's Models API returns no capability flags, so capability handling must be per-provider. Items that rest on weak or missing primary sources are separated as UNVERIFIED at the end.

## Apple's HIG supplies the structure; OpenAI's guidelines only the polish

OpenAI's UI pages target plugin widgets inside a ChatGPT conversation: inline cards, carousels of 3-8 items, fullscreen and picture-in-picture modes, a maximum of two card actions, and no nested scrolling ([OpenAI UI guidelines](https://developers.openai.com/plugins/concepts/ui-guidelines)). None of that maps to a window with a sidebar, toolbar and inspector. What does transfer is stylistic: inherit the system font stack, use system colors, keep brand accents to icons and primary buttons, use monochrome outlined icons, "Don't use custom fonts, even in full screen modes" ([OpenAI design guidelines](https://developers.openai.com/apps-sdk/concepts/design-guidelines)), and meet WCAG AA contrast with alt text and text-resize tolerance. OpenAI also states that errors "must be handled with clear messaging or fallback behaviors" and that irreversible operations need human confirmation ([OpenAI plugin guidelines](https://developers.openai.com/plugins/plugin-guidelines)), a useful reinforcement for any AI-triggered action in Paladin. OpenAI gives no loading, empty-state, form or keyboard guidance, and no desktop-app guideline or Codex design page was found, so Apple fills every gap.

Apple's window and toolbar rules are the most checkable. A toolbar has three zones (leading, center, trailing), at most about three groups, borderless symbols in preference to text, one primary action on the trailing side, a title under 15 characters that is not the app name, and every toolbar item must also exist as a menu-bar command ([Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)). Apple says to avoid custom window frames and controls ([Windows](https://developer.apple.com/design/human-interface-guidelines/windows)), which in Electron means keeping the native traffic lights via `titleBarStyle: 'hiddenInset'` or `hidden` ([Electron custom title bar](https://www.electronjs.org/docs/latest/tutorial/custom-title-bar)). Critical information must not sit at the bottom edge of a window, because users drag windows partly off-screen ([Windows](https://developer.apple.com/design/human-interface-guidelines/windows)); that matters for a graph canvas with a bottom legend or timeline. The toolbar guidance was updated for Liquid Glass on December 16, 2025: avoid custom toolbar backgrounds and tinted controls, and let content drive color ([Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)). Electron cannot render true Liquid Glass; the honest approximation is `vibrancy` materials on the functional layer only ([Materials](https://developer.apple.com/design/human-interface-guidelines/materials)).

Sidebars, split views and inspectors carry the information architecture. A sidebar shows no more than two hierarchy levels, uses accent-colored symbols by default, can be shown and hidden, and is never hidden by default ([Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)). Split-view dividers are draggable, the thin style is **1 pt** wide, panes need sensible min and max sizes, and hidden panes need a toolbar button, a menu command and a shortcut ([Split views](https://developer.apple.com/design/human-interface-guidelines/split-views)). The inspector updates with selection and uses the same reveal rules; Apple lists **Option-Command-I** as the standard inspector shortcut and Option-Command-T for the toolbar ([Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)). Because the sidebar and inspector also bracket the graph, selection must stay highlighted persistently in each pane that leads to a detail ([Split views](https://developer.apple.com/design/human-interface-guidelines/split-views)). Lists and tables sort by clicking column headings, allow column resizing, and use a middle ellipsis for clipped identifiers ([Lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables)), which suits long hostnames, ARNs and paths in attack-path results. Outline views retain expansion state and put hierarchy only in the first column ([Outline views](https://developer.apple.com/design/human-interface-guidelines/outline-views)).

## Type, color, hit targets and motion have published numbers

Apple's macOS type table is exact: Body **13/16 pt**, Callout 12/15, Subheadline 11/14, Footnote and Caption 10/13, Headline 13/16 bold, Title 3 15/20, with a **10 pt minimum**, no Dynamic Type on macOS, and thin weights discouraged ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography)). Control hit targets default to **28x28 pt** with a **20x20 pt** minimum, with about 12 pt padding around bezeled elements and about 24 pt around unbezeled ones ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). Text contrast must reach 4.5:1, and Apple's Dark Mode page recommends 7:1 for custom pairs, especially small text ([Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)). Paladin must follow system Light/Dark/Auto without an app-specific appearance setting, test with Increase Contrast and Reduce Transparency, and never convey severity by color alone ([Color](https://developer.apple.com/design/human-interface-guidelines/color)). That last rule is the sharpest for a security graph: critical, high and medium nodes need shape, icon or label redundancy. Electron exposes the hooks: `nativeTheme.themeSource`, `nativeTheme.prefersReducedTransparency` and `systemPreferences.getAccentColor()` ([nativeTheme](https://www.electronjs.org/docs/latest/api/native-theme), [systemPreferences](https://www.electronjs.org/docs/latest/api/system-preferences)).

Motion guidance is qualitative: purposeful, brief, cancelable, and under reduced motion replace spatial transitions with fades ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). Apple publishes no durations, so a 150-250 ms budget is practice, not HIG. Progress should be determinate when possible, avoid vague "loading" copy, and include Cancel when safe ([Progress indicators](https://developer.apple.com/design/human-interface-guidelines/progress-indicators)); this applies directly to long graph analyses and LLM runs.

## Menus, shortcuts, settings and alerts are where Electron apps most often fail

The menu bar order is App, File, Edit, Format, View, app-specific, Window, Help; the App menu starts with About, then Settings… at **Command-Comma**; View holds Show/Hide Sidebar, Show/Hide Toolbar and Enter/Exit Full Screen ([The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)). Unavailable items are dimmed, not hidden, and ellipses mark commands that need more input ([Menus](https://developer.apple.com/design/human-interface-guidelines/menus)). Custom shortcuts use Command as the main modifier, must not repurpose standard shortcuts, and list modifiers in Control, Option, Shift, Command order ([Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)). Electron menu roles (`appMenu`, `editMenu`, `viewMenu`, `windowMenu`) give localized native behavior for free ([MenuItem](https://www.electronjs.org/docs/latest/api/menu-item)). Apple has no command-palette page; the defensible approach is to treat it as a search field (type-to-filter, recents, categories, Esc to dismiss) over commands that also exist in the menu bar, avoiding Command-Space ([Search fields](https://developer.apple.com/design/human-interface-guidelines/search-fields)).

Settings open from the App menu, never from a main-toolbar button; they use toolbar-tab panes whose title tracks the visible pane, reopen to the last pane, and favor few options with good defaults ([Settings](https://developer.apple.com/design/human-interface-guidelines/settings)). Provider keys fit onboarding's rule that required setup may be requested up front while nonessential setup is postponed ([Onboarding](https://developer.apple.com/design/human-interface-guidelines/onboarding)). Alerts are used sparingly, carry at most three buttons with specific verbs, keep Cancel titled "Cancel", never make Cancel the default, and destructive alerts always include Cancel ([Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts)). Errors are shown near the problem, say how to fix it and avoid "Oops" ([Writing](https://developer.apple.com/design/human-interface-guidelines/writing)); provider errors (bad key, spend cap, overloaded) should follow this.

## Two providers, one interface, deliberately uneven capabilities

Claude authenticates with `x-api-key` (or Bearer), `anthropic-version: 2023-06-01` and JSON content type against `https://api.anthropic.com` ([API overview](https://platform.claude.com/docs/en/api/overview)); multi-workspace keys also need `anthropic-workspace-id` ([Authentication](https://platform.claude.com/docs/en/manage-claude/authentication)). OpenAI uses `Authorization: Bearer`, with optional `OpenAI-Organization` and `OpenAI-Project` headers, and `x-request-id` on every response ([OpenAI API overview](https://developers.openai.com/api/reference/overview)). Neither documents a dedicated validate-key endpoint; `GET /v1/models` is the cheap authenticated call on both, which is an inference. A 200 there does not prove billing allows inference, since Claude's 402 and spend-cap errors appear only on Messages calls ([Errors](https://platform.claude.com/docs/en/api/errors)).

Model discovery is richer on Claude. `GET /v1/models` returns `lifecycle`, `retires_at`, `max_tokens`, `max_input_tokens`, and a `capabilities` object covering structured outputs, thinking, effort, image and PDF input ([List Models](https://platform.claude.com/docs/en/api/models-list)). The current lineup is Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5 (Sonnet 5.5 at $2/$10 per MTok with 1M context; Haiku 5.5 from $0.10/$0.50), and the docs say to start with Opus 5.5 for most workloads ([Models overview](https://platform.claude.com/docs/en/models/overview)). OpenAI's Models API returns only `id`, `created`, `owned_by` and optional `shutdown_date` ([Models reference](https://developers.openai.com/api/reference/resources/models)), so capability filtering needs an app-maintained allowlist. OpenAI's own docs are internally inconsistent on flagship IDs (`gpt-6-astra`, `gpt-6.1-sol`, `gpt-5.6-sol` all appear), so IDs must come from the live list ([Models](https://developers.openai.com/api/docs/models)).

Request parameters diverge in ways that bite. On Claude models released after Opus 4.6, `temperature` other than 1.0 returns 400, `top_k` is rejected, and prefill is rejected ([Create a Message](https://platform.claude.com/docs/en/api/messages/create), [Errors](https://platform.claude.com/docs/en/api/errors)). Forced `tool_choice` (`any` or `tool`) returns 400 on Opus 5.5, Sonnet 5.5 and Fable 5.1 ([Errors](https://platform.claude.com/docs/en/api/errors)), so structured analysis results should use `output_config.format` JSON schema, which requires `additionalProperties:false` and forbids recursive schemas and numeric or length bounds ([Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). On the OpenAI side, the Responses API is recommended for new projects ([Migrate to Responses](https://developers.openai.com/api/docs/guides/migrate-to-responses)), strict function schemas need every property required ([Function calling](https://developers.openai.com/api/docs/guides/function-calling)), and `max_output_tokens` includes reasoning tokens, so hitting it can return `incomplete` with no visible output ([Reasoning](https://developers.openai.com/api/docs/guides/reasoning)). Thinking is adaptive on Claude 5.x and 400s if set to manual budgets on 4.7+; steer with `output_config.effort` ([Thinking](https://platform.claude.com/docs/en/build-with-claude/thinking)). OpenAI's effort values are model dependent and some models reject `none` ([Reasoning](https://developers.openai.com/api/docs/guides/reasoning)).

Streaming shapes differ but normalize cleanly. Claude emits `message_start`, `content_block_start/delta/stop`, `message_delta`, `message_stop`, plus `ping` and `error`; tool input arrives as `input_json_delta` fragments parsed at block stop; overload can arrive as an `error` event inside a 200 stream ([Streaming](https://platform.claude.com/docs/en/build-with-claude/streaming)). OpenAI's Responses stream includes lifecycle events (`response.created`, `response.queued`, `response.in_progress`), output-item and content-part events, text and refusal deltas, reasoning-summary events, function-call-argument events, and the terminal `response.completed`, `response.failed`, and `response.incomplete` events. Paladin emits text/refusal deltas, maps terminal events, and deliberately ignores progress and tool events because the Assistant does not run a tool loop ([Streaming events](https://platform.openai.com/docs/api-reference/responses-streaming)). Stop conditions to surface as user-visible states rather than failures are Claude's `refusal` (HTTP 200), `max_tokens`, `pause_turn` and `model_context_window_exceeded` ([Handling stop reasons](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)), and OpenAI's `incomplete` and `refusal` content parts ([Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs)).

Error handling is similar in spirit and different in detail. Claude's codes are 400, 401, 402, 403, 404, 413, 429, 500, 504 and 529, with `request-id` in header and body ([Errors](https://platform.claude.com/docs/en/api/errors)). A spend-cap 429 carries `enforced_spend_limit_reached` and no `retry-after`, resuming only at 00:00 UTC on the first of the next month, so it must not be retried ([Rate limits](https://platform.claude.com/docs/en/api/rate-limits)). OpenAI overloads 429 with both rate limits and quota errors, so the app must branch on `error.code` (for example `credit_balance_exhausted`, `organization_spend_limit_exceeded`), retry only genuine rate limits and 5xx, honor `Retry-After` as a minimum, and avoid nested retries with the SDK ([Error codes](https://developers.openai.com/api/docs/guides/error-codes), [Rate limits](https://developers.openai.com/api/docs/guides/rate-limits)). Both official Python SDKs retry twice by default on 408, 409, 429 and 5xx, default to a 10-minute timeout, and expose `_request_id` ([Claude Python SDK](https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/python), [openai-python](https://raw.githubusercontent.com/openai/openai-python/main/README.md)). Neither retries once a stream has started, so mid-stream recovery is Paladin's job; on Claude 4.6+ that means a user message containing the partial and a continue instruction, since prefill is rejected ([Streaming](https://platform.claude.com/docs/en/build-with-claude/streaming)).

## Key handling is the Electron-specific risk, and loopback is not authentication

Electron's `safeStorage` is main-process only, uses Keychain on macOS, protects against other users and offline disk access but not other apps running as the same user, and has an async API that the docs recommend over the sync one ([safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)). On Linux, a `basic_text` backend means effectively unprotected storage and should be refused or warned about. Keychain behavior depends on code signing; unsigned builds re-prompt after updates ([Code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)). Electron's security checklist requires context isolation, sandboxing, a CSP, limited navigation, denied new windows and sender validation in every IPC handler ([Security](https://www.electronjs.org/docs/latest/tutorial/security)); with a UI served from `http://127.0.0.1`, each check must compare the parsed origin including port. The IPC docs advise one narrow bridge method per message, `invoke`/`handle`, and never exposing `ipcRenderer` wholesale ([Context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation)). The note author's reading is that another local process could claim the loopback port, so a per-launch bearer token on the backend is prudent, though no Electron source recommends it.

Anthropic itself says to store keys in a secrets manager and rotate them ([Authentication](https://platform.claude.com/docs/en/manage-claude/authentication)), and OpenAI says keys must not be exposed in browsers or apps ([OpenAI API overview](https://developers.openai.com/api/reference/overview)). For BYOK desktop apps the closest compliant pattern is OS-keychain at rest, backend memory at runtime. Data policy matters to a security product: Claude API content is not retained by default, but Fable and Mythos 5.x are Covered Models requiring 30-day retention, and flagged content may be kept up to two years ([API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)). OpenAI keeps abuse-monitoring logs up to 30 days and `store` controls application-state retention ([Your data](https://developers.openai.com/api/docs/guides/your-data)); defaulting to `store:false` is an inference consistent with that page.

## Conclusion

The report's main finding is an asymmetry: Apple's rules are concrete enough to audit line by line, yet silent exactly where Paladin is most novel (graph canvas, command palette, minimum window size), while the two provider APIs are well documented but incompatible on the details that break abstractions (forced tool choice, sampling parameters, error semantics for 429, capability discovery). The right response is a thin provider interface whose per-provider adapters own parameter clamping and error classification, and a UI audit that marks each rule as HIG-sourced, Electron-inferred or Paladin-defined so reviewers do not mistake convention for Apple policy.

Two risks deserve early attention. First, key custody: `safeStorage` is at-rest protection only, and a same-user attacker defeats every option, so the design minimizes exposure rather than eliminating it, and a signed, notarized build is a prerequisite for sane Keychain behavior. Second, source quality: the notes were gathered through a summarizing fetch tool, and model IDs and prices from both vendors changed fast and are partly inconsistent, so model names and numeric limits should be re-verified against live pages before they are hard-coded.

## Checklist 1: auditable UI design rules

Each rule is checkable by inspection. Source tags: HIG = Apple page cited above; ELEC = Electron docs; OAI = OpenAI page; INF = inference, not vendor policy.

1. Window controls are the native traffic lights; no custom close/minimize/zoom drawn in the DOM (HIG Windows; ELEC `hiddenInset`).
2. Window title is a short noun phrase under 15 characters and is not the app name, or is empty when redundant (HIG Toolbars).
3. The toolbar has at most three groups, one prominent primary action on the trailing side, borderless symbol buttons, and no "Back" or "Close" text labels (HIG Toolbars).
4. Every toolbar button has an equivalent menu-bar command (HIG Toolbars).
5. No custom toolbar background or tinted controls; vibrancy used only on sidebar and toolbar layers, never on content (HIG Toolbars, Materials; INF for Electron mapping).
6. No critical information or actions at the bottom edge of the window (HIG Windows, Sidebars).
7. Menu bar order is App, File, Edit, View, app-specific, Window, Help; App menu has About first, then Settings… with Command-Comma, then Services, Hide, Hide Others, Show All, Quit (HIG The menu bar).
8. View menu contains Show/Hide Sidebar, Show/Hide Toolbar, Enter/Exit Full Screen; Edit menu has Undo, Redo, Cut, Copy, Paste, Select All, Find (HIG The menu bar).
9. Unavailable menu items are dimmed, not hidden; commands needing more input end with an ellipsis (HIG Menus).
10. No standard shortcut is repurposed; custom shortcuts use Command as the base modifier and list modifiers Control, Option, Shift, Command (HIG Keyboards).
11. Sidebar shows at most two hierarchy levels, is visible by default, and has a toolbar button, a menu command and a shortcut to hide/show (HIG Sidebars, Split views).
12. Sidebar icons are monochrome symbols tinted with the system accent color; fixed colors only where color carries meaning (HIG Sidebars; INF for Electron).
13. Split-view dividers are draggable, 1 pt thin, with min/max pane sizes that keep the divider visible; the inspector can be hidden via button, menu and Option-Command-I (HIG Split views, Keyboards).
14. Selection is persistently highlighted in the sidebar, results list and graph canvas, and the inspector updates with selection (HIG Split views, Panels).
15. Tables sort by header click and reverse on second click, columns are resizable, headings are short nouns, clipped identifiers use a middle ellipsis (HIG Lists and tables).
16. Outline/tree views keep expansion state across navigation and place hierarchy in the first column (HIG Outline views).
17. Body text is 13 px with 16 px line height, nothing below 10 px, no Ultralight/Thin/Light weights, system font stack (HIG Typography; INF for CSS px mapping).
18. Interactive controls are at least 20x20 and default 28x28 pt, with about 12 pt padding around bezeled controls (HIG Accessibility).
19. Text contrast is at least 4.5:1 in light, dark and increased-contrast modes; custom small-text pairs target 7:1 (HIG Accessibility, Dark Mode).
20. Appearance follows system Light/Dark/Auto live; there is no in-app theme override (HIG Dark Mode).
21. Severity, risk and node state are never encoded by color alone; each has a shape, icon or text label (HIG Color).
22. Semantic color tokens are used; no hard-coded system color values, and graph colors have light, dark and increased-contrast variants (HIG Color).
23. `prefers-reduced-motion`, `prefers-contrast` and `prefers-reduced-transparency` are honored; reduced motion replaces spatial transitions with fades (HIG Accessibility; INF for CSS media query mapping).
24. Every icon-only control has an accessible name; the full UI is operable with the keyboard (HIG Accessibility, Keyboards; OAI alt-text rule).
25. Settings open only from the App menu (no main-toolbar settings button), use tabbed panes titled after the visible pane, and reopen to the last pane (HIG Settings).
26. Provider key entry uses a secure (masked) field with a visible label, not placeholder-only, and is requested at setup because the app needs it to function (HIG Text fields, Onboarding).
27. Alerts have at most three buttons with specific verbs; Cancel is titled "Cancel", is never the default, and always appears with destructive actions; Esc and Command-Period cancel (HIG Alerts).
28. Error copy states what happened and how to fix it, shown near the problem, with no "Oops" or blame (HIG Writing; OAI error-handling rule).
29. Long operations use determinate progress where possible and expose Cancel (HIG Progress indicators).
30. Popovers are single and small; sheets are one at a time and modal; neither is used for warnings (HIG Popovers, Sheets).
31. Command palette is searchable as the user types, shows recents, groups by category, dismisses with Esc, does not use Command-Space, and only lists commands that also exist in the menu bar (HIG Search fields; INF, Apple has no palette page).
32. No custom fonts and no custom gradients on structural UI; brand color limited to icon, badge and primary-button accents (OAI design guidelines; HIG Color).
33. AI-initiated write or irreversible actions require explicit user confirmation (OAI plugin guidelines).
34. Window is resizable and layouts adapt fluidly; the minimum size is Paladin-defined (HIG Windows; INF, Apple gives no number).

## Checklist 2: provider-integration design

### Verified or directly supported by primary docs

1. Use the official async SDKs (`AsyncAnthropic`, `AsyncOpenAI`) inside FastAPI, with exact versions pinned and one shared client per key; pass model IDs as plain strings.
2. Anthropic requests carry `anthropic-version: 2023-06-01`; add `anthropic-workspace-id` only when the key is multi-workspace; map 400/404 workspace errors to a "workspace" message. OpenAI sends Bearer, with optional org and project headers.
3. Model lists come from `GET /v1/models` at runtime. For Claude, filter on `lifecycle`, group by `line`, gate features on `capabilities`, cap `max_tokens` at the model value and show `retires_at`. For OpenAI, hide models with `shutdown_date` set.
4. Do not send `temperature`, `top_k`, or prefill to Claude 5.x models; never use forced `tool_choice` on Opus 5.5, Sonnet 5.5 or Fable 5.1.
5. Structured results on Claude use `output_config.format` JSON schema (flat, all fields required, `additionalProperties:false`), validated again with Pydantic; on OpenAI use `text.format` with `strict:true`.
6. Tool loops: Claude returns `tool_result` blocks first in one user message per `tool_use` turn; OpenAI returns `function_call_output` keyed by `call_id`. Cap iterations and total tokens in app code.
7. Claude thinking is adaptive on 5.x; control with `output_config.effort`. Pass thinking blocks back unmodified within tool loops. For OpenAI, clamp `reasoning.effort` to values the chosen model accepts and reserve ample `max_output_tokens`.
8. Stream with SSE: ignore unknown Claude events, accumulate `input_json_delta` and parse at block stop, treat in-stream `error` as the terminal condition, and surface `refusal`, `max_tokens`, `incomplete` as states.
9. Retry 408/409/5xx/529 and genuine 429s with exponential backoff and jitter, honoring `retry-after`; never retry 401, 402, 403, Claude `enforced_spend_limit_reached`, or OpenAI quota and spend-limit codes (branch on `error.code`). Keep SDK retries at 2 or disable them to avoid nested retries.
10. Log `request-id` / `x-request-id` and rate-limit headers only; never log `x-api-key`, `Authorization` or request bodies by default.
11. Keys are encrypted with `safeStorage` async APIs in the Electron main process after `ready`; refuse or warn on the Linux `basic_text` backend; ship a signed, notarized build.
12. IPC exposes `setKey(provider, value)` write-only, `hasKey(provider)`, `removeKey(provider)`; no channel returns a key; every handler validates `senderFrame` origin (null-checked) and schema-validates arguments.
13. Renderer CSP `connect-src` allows only the backend origin; renderer never contacts Anthropic or OpenAI; navigation, window open and permission handlers pin to the exact loopback origin; disable fuses `runAsNode`, `nodeOptions`, `nodeCliInspect`.
14. Redact secrets in prompts before sending where feasible, disclose that content leaves the device, and show the provider's retention posture (Claude Covered Models need 30-day retention; OpenAI `store:false` default).

### UNVERIFIED or inference-only (confirm before relying)

1. `GET /v1/models` as the key-validation call for both providers; a 200 does not prove billing or spend limits permit inference.
2. Passing the key from main to the Python backend over stdin or an inherited pipe (preferred) rather than env; no Electron doc prescribes a pattern, and macOS `ps` environment visibility lacks a vendor source.
3. A per-launch random bearer token and random port for the loopback backend; not an Electron-documented recommendation.
4. Streaming cancellation semantics and billing for aborted streams on both providers (closing the connection is the assumed mechanism).
5. OpenAI exact flagship model IDs and the "chat-capable" filter by ID substring; the Models API has no capability fields. Record the IDs returned to the test account before changing the filter.
6. Which OpenAI model IDs accept each reasoning-effort value. `/v1/models` does not advertise this capability, so the live list alone cannot establish effort support; a minimal Responses request per model and effort is required.
7. OpenAI error JSON envelope field layout, project-key prefix behavior, and the Responses `create` reference (HTTP 403 to the fetch tool). The Responses reference does confirm that `instructions` is equivalent to a developer message.
8. Claude Retrieve-model endpoint shape, SDK version numbers and the printed `httpx2` requirement; verify against the installed package.
9. OpenAI-compatible local servers (Ollama, LM Studio, vLLM): assume Chat Completions only and capability-probe; no primary doc.
10. Apple numerics not on HIG pages: minimum window size, traffic-light inset, sidebar row heights (24/28/32 pt is a commonly cited AppKit figure), inspector width, table row height, animation durations, focus-ring specification, and exact macOS system color values.
11. Windows Hello or other non-macOS secret-reveal gating has no Electron API found; `promptTouchID` is a UI gate only, not cryptographic protection.
12. Whether Anthropic's `ANTHROPIC_LOG=debug` redacts keys, and the standard commercial log retention periods (privacy.claude.com not fetched).
